## 설계 문서

`docs/internal/`의 설계 문서는 소스코드만 봐서는 "왜 이렇게 했는가?"가 풀리지 않는 결정과 복잡한 동작을 기록한다. 에이전트가 코드를 읽기 전에 의도를 파악하게 하는 문서다. 사소한 것은 소스코드를 직접 읽게 한다.

기록하는 경우 (하나라도 해당):

- 코드를 보면 "왜 이렇게 했지?" 하고 의문이 드는 결정이다.
- 더 나은 방법이 있어 보이는데 제약 때문에 다르게 구현했다.
- 흐름이 복잡해서 코드를 읽어도 전체 구조를 파악하기 오래 걸린다.

예: circumcenter 계열이 degenerate guard와 denominator를 같은 float 전개로 묶는 이유.

기록하지 않는 경우:

- 코드와 타입에서 바로 읽히는 내용. 소스를 직접 읽는다.
- 한 함수 안에서 끝나는 구현 방식. TSDoc에 둔다.
- 한 작업의 진행 과정과 임시 결정. `_works/`와 커밋 메시지에 둔다.
- 에이전트가 반복한 실수. `docs/internal/agent-traps/`에 둔다.

`docs/internal/adr/`와의 구분:

- `docs/internal/adr/`: 방향. 되돌리기 비싼 큰 결정과 대안 비교를 적는다. "무엇을 선택했고 무엇을 버렸는가"다.
- `docs/internal/`의 설계 문서: ADR의 방향을 코드에서 실현한 구조적 설계. 모듈 경계, 흐름, 책임 분담을 적는다.
- 방향을 바꾸는 결정은 ADR에 쓴다. 설계 문서는 근거가 되는 ADR을 가리킨다.
- ADR 없이 코드의 구조적 결정만 있으면 설계 문서만 쓴다.

기록 규칙:

- 기존 문서(`architecture.md`, `api-design.md`, `precision.md` 등)에 맞는 주제면 그 문서에 절을 추가한다.
- 새 문서를 만들면 `docs/internal/README.md` 색인 표에 한 줄을 추가한다.
- 현재 시점의 내용만 적는다. 소스 줄 번호를 적지 않는다.
- 무효가 된 문서의 처리는 `writing-styles.md`의 "수명"을 따른다.
- 기록할지 애매하면 쓰기 전에 사용자에게 묻는다.
- `_works/`, `_tmp/`, `docs/superpowers/`는 Git 추적 대상이 아니다.

## 브랜치와 커밋

레인 여부와 관계없이 적용한다. 전역 지시의 Git 규칙(커밋 메시지 형식, push는 요청 시)에 더한 이 저장소의 규칙이다.

- `main`은 GitHub `origin/main`과 맞추는 공개 브랜치다. CI는 `main` push와 PR에서 돈다.
- `dev`는 로컬 통합 브랜치다. `main`에서 만들었다.
- npm 배포는 유지보수자가 `main`에서 직접 한다. 절차는 `RELEASING.md`를 따른다.
- 작업은 `dev`에서 임시 작업 브랜치를 만들어 진행한다. 이름은 `<커밋 타입>/<작업 slug>`다. 시작 전에 `git status --short`가 깨끗한지 확인한다.
- 간단한 작업은 작업 브랜치 없이 `dev`에서 직접 진행하고 커밋해도 된다.
  - 간단한 작업은 목표와 변경 범위가 명확하고 위험이 낮은 작업이다.
  - 관련 검증과 변경 범위 확인을 한 번에 마칠 수 있어야 한다.
  - 예: 짧은 문서 문구 수정, 작은 국소 변경.
  - 해당 파일만 선택해 커밋한다.
- 워크플로 레인(qq-workflow, roadmap-workflow) 작업은 간단해 보여도 작업 브랜치를 쓴다. 착수 커밋 기준 비교가 필요하기 때문이다.
- 작업 브랜치에서는 에이전트가 판단해 자유롭게 커밋한다.
- 작업이 끝나면 `dev`로 squash 병합해 커밋 수를 줄인다. 기본은 커밋 1개다. 절차는 `workflow-shared.md`의 "병합"을 따른다.
- 작업 브랜치의 커밋과 `dev` 병합은 묻지 않고 에이전트 판단으로 진행한다.
- `main` 병합, push, PR 생성은 지시가 있을 때만 한다.
- 패키지 사용자에게 보이는 변경은 같은 커밋에서 `CHANGELOG.md`의 `## [Unreleased]`에 항목을 추가한다.
- `dev`에는 `main`에 병합하지 않은 커밋이 많을 수 있다. 작업 시작 시점의 `dev` 커밋을 착수 커밋으로 기록하고, 변경 비교는 `git diff <착수 커밋>`으로 한다. 워크플로 작업은 계획서의 `착수 커밋` 절에 적는다.

## 작업 레인

계획서를 남기고 결과물을 리뷰하는 작업 흐름은 두 가지다.

| 레인             | 대상                                                       | 절차 문서                                |
| ---------------- | ---------------------------------------------------------- | ---------------------------------------- |
| qq-workflow      | DELTA 하나 크기(목표 1,000줄), 독립 결과 1개               | [qq-workflow.md](./qq-workflow.md)       |
| roadmap-workflow | 그보다 큰 작업. RD(DELTA 2~4개, 최대 8개) 단위로 통합 리뷰 | [roadmap-workflow.md](./roadmap-workflow.md) |

공통 계약(DELTA 크기, Git, 검증 게이트, 리뷰 기록): [workflow-shared.md](./workflow-shared.md)

레인 선택 규칙:

- 사용자가 레인을 지목하면 그 레인으로 진행한다.
- 레인 없이 워크플로우 진행을 요청하면 예상 변경으로 판정한다. DELTA 하나 크기에 독립 결과가 1개면 qq-workflow, 아니면 roadmap-workflow. 선택한 레인과 이유를 작업 시작 시 한두 문장으로 보고한다.
- 워크플로우 요청이 없으면 레인 없이 진행한다. `_works` 문서를 만들지 않는다.
- 레인은 시작할 때 정하고 중간에 바꾸지 않는다. qq 작업이 커지면 멈추고 보고하며 판단은 사용자가 한다.

작업 폴더: `_works/<yyyyMMdd>-<seq>-<한글작업명>/`.

- `<seq>`는 `01`, `02` 같은 두 자리 일련번호다.
- `_works/`는 Git에서 제외한다.
- 작업이 끝나면 에이전트가 폴더를 `_works/_completed/`로 옮긴다. 절차는 `workflow-shared.md`의 "작업 폴더 보관"을 따른다.
- 템플릿은 `templates/`에 있다. 문서는 필요한 단계에서 만든다.
- 템플릿 파일명의 `qq-`, `roadmap-` 접두사는 작업 폴더에 복사할 때 뺀다.
